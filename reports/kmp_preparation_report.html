Отчет по рекомендуемому пути подготовки проекта к KMP

Проект: elta-android
Дата: 08.04.2026
Формат: технический отчет по результатам анализа Android-версии приложения

1. Цель отчета

Определить, какой путь развития проекта является технически оправданным: немедленный переход на Kotlin Multiplatform, массовая перепись текущего Android-стека или поэтапная подготовка архитектуры к будущему shared-слою.

2. Основание для выводов

Выводы сделаны на основе разбора структуры модулей, Gradle-конфигурации, зависимостей, состава слоев app/presentation/domain/data/common/core/iiot-sdk, а также по факту использования Android API, RxJava2, Dagger, ObjectBox, Room, BLE, Health Connect, Google Fit, Firebase, OneSignal, Webim и других платформенных интеграций.

3. Текущее состояние проекта

Параметр Наблюдение
Общий объем Kotlin-кода Около 107 485 строк
Слой presentation Около 65 755 строк, 121 Fragment, 118 Pm-классов, 49 ViewModel, 85 Compose-файлов, 132 XML layout
Слой data Около 19 492 строк, содержит сеть, хранилище, Android SDK, BLE, push, background integration
Слой domain Около 7 588 строк, но уже содержит Android-типы, RxJava2, Dagger и platform-specific зависимости
Тесты Покрытие слабое для безопасной большой миграции
Проект уже модульный, но эта модульность не является KMP-ready. Это Android/JVM-модульность, а не разделение на действительно платформенно-независимое ядро и платформенные адаптеры.

4. Главная проблема текущего состояния

Основная проблема не в XML и не в том, что проект пока не на KMP. Основная проблема в том, что границы слоев размыты. В частности:

  • domain уже зависит от Android-типов и Android-сценариев;
  • data смешивает бизнес-преобразования и прямую работу с Android SDK;
  • RxJava2 глубоко встроен в API слоев и в способы взаимодействия между ними;
  • часть use case уже несет в себе платформенную логику вместо чистой бизнес-логики.

В таком состоянии прямой старт с KMP не даст аккуратный shared-слой. Он превратится в большой рефакторинг под видом миграции.

5. Оценка возможных стратегий

5.1. Вариант: сразу переходить на KMP

Оценка: не рекомендован как первый шаг.

Причины:

  • в текущем виде переносить в commonMain почти нечего без предварительной чистки слоев;
  • проект слишком завязан на Android API и Android-only SDK;
  • возрастает риск затяжной миграции без быстрой прикладной отдачи;
  • сложно безопасно переносить бизнес-логику, пока она смешана с платформенными деталями.

Вывод: KMP для этого проекта сейчас не стартовая точка, а следующий этап после подготовки архитектуры.

5.2. Вариант: переписать весь RxJava и весь XML разом

Оценка: также не рекомендован.

Причины:

  • это еще один big bang с высоким риском регрессий;
  • массовая перепись XML не решает проблему границ слоев;
  • XML не мешает будущему KMP, если UI остается нативным;
  • перепись всего RxJava одним заходом слишком дорогая и тяжело контролируется по качеству.

Вывод: переписывать весь UI и весь reactive-стек одновременно сейчас нецелесообразно.

5.3. Вариант: постепенно выдавливать RxJava из domain/data и чистить границы слоев

Оценка: рекомендованный путь.

Причины:

  • дает ценность даже без KMP;
  • уменьшает зависимость бизнес-логики от Android;
  • готовит проект к shared-слою без остановки всей разработки;
  • снижает стоимость и риск будущего перехода на KMP.

6. Рекомендуемое решение

Для этого проекта рекомендуется следующий подход:

  1. не делать немедленный переход на KMP;
  2. не запускать массовую перепись всего UI;
  3. сначала очистить domain от Android-типов и RxJava-зависимостей в публичных контрактах;
  4. затем привести в порядок data, разделив чистую логику и Android-адаптеры;
  5. после этого выделить один или несколько реально platform-free модулей;
  6. только затем оформлять их как KMP shared-модули.
Короткая формулировка рекомендации: сначала сделать проект пригодным для KMP, потом подключать KMP.

7. Что нужно делать первым

7.1. Очистка слоя domain

На первом этапе требуется:

  • убрать из контрактов `Uri`, `Bitmap`, `PagingData`, `Parcelable` и аналогичные Android-зависимые типы;
  • перевести API use case и repository на `suspend` и `Flow` там, где это допустимо по смыслу;
  • убрать `blockingGet()` и подобные синхронные мосты;
  • отделить бизнес-модели от моделей, ориентированных на Android-реализацию.

Результат этапа: `domain` начинает становиться реальным business/core-слоем, а не Android-friendly фасадом поверх текущей реализации.

7.2. Очистка слоя data

На втором этапе требуется:

  • оставить Android-only интеграции в platform-адаптерах;
  • вынести чистые преобразования, мапперы, DTO и правила синхронизации в более нейтральный слой;
  • ограничить использование `Context`, permissions, system services, `Service`, `BroadcastReceiver` внутри Android-части;
  • не пытаться тащить BLE, push, chat SDK, vendor SDK и background integration в общий слой.

7.3. Подготовка к KMP

После очистки `domain/data` нужно:

  • выделить один platform-free модуль;
  • перенести туда 1-2 фичи с высокой долей чистой логики;
  • покрыть этот слой тестами;
  • только затем оформлять его как KMP shared.

8. Что пока не стоит трогать

На начальном этапе не рекомендуется массово переписывать:

  • весь XML в Compose;
  • весь `presentation`;
  • всю навигацию;
  • BLE и firmware update;
  • push, analytics, maps, chat, social SDK;
  • background integration и reminders.

Причина одна: это резко раздует объем миграции, но не приблизит проект к качественному shared-слою в краткосрочном горизонте.

9. Ожидаемый эффект от рекомендованного пути

  • снижение технического риска по сравнению с немедленным KMP;
  • очищение `domain` и `data` без остановки текущей Android-разработки;
  • уменьшение платформенной связанности логики;
  • упрощение тестирования и сопровождения;
  • создание реальной базы для KMP, а не формального shared-модуля;
  • контролируемая миграция по частям вместо полной архитектурной ломки.

10. Итоговый вывод

Для текущего состояния проекта правильный путь выглядит так:

  1. не начинать с KMP;
  2. не делать тотальную перепись RxJava и XML;
  3. сначала постепенно выдавить RxJava из domain/data;
  4. очистить границы слоев;
  5. после этого запускать KMP как следующий шаг.

Это решение для данного проекта является наиболее устойчивым по срокам, рискам и техническому качеству.
